| E12 | 2026-11-05 | `/forecast/{id}/summary` kWh now uses the real timestep: median positive gap between forecast timestamps (fallback 1 minute with <2 distinct timestamps), `kWh = sum(kW) * dt_hours`. SolarPulse divided by 60 (assumed 1-minute spacing), understating 15-minute data 15x. At exactly 1-minute spacing the result is identical. No golden test covered this function (golden cases cover only pure postprocessing/diagnosis/weather helpers), so no expected value changed; new tests in `test_forecast_summary_spacing.py` cover 1/5/15/60-minute, irregular and single-record series and a hand-computed example. With forecasts generated ad hoc at irregular times the median gap is only an approximation; a sum over a regular grid is the intended use. | Energy totals must not depend on an unstated sampling assumption. |

| E13 | 2026-11-05 | Single-axis tracker plants (PVDAQ 9068). `physics/tracker.py`: `is_tracker_plant(plant)` reads the marker `[single-axis tracker, fixed-tilt baseline invalid]` in `plants.location` (no mount column exists; no migration added). Policy: every request that needs the fixed-tilt baseline returns **HTTP 422** `detail={"status":"baseline_unsupported_for_trackers","message":...}` (chosen over a labelled null so the status is identical on every endpoint): `solar.expected_power` itself raises (so `POST /forecast/{id}/generate`, `GET /forecast/{id}/probabilistic`), and `POST /diagnosis/diagnose` with no request power values (its telemetry fallback uses the stored fixed-tilt expected power). Caller-supplied expected/actual are used as given. `run_alert_check` skips tracker plants and `detect_and_persist_anomaly` never creates an alert for them, so no deficit alert comes from the fixed-tilt baseline. Everything for fixed plants is unchanged. **pvlib single-axis model NOT enabled.** Prototype (scratch, not shipped): `pvlib.tracking.singleaxis` (axis_tilt 0, axis_azimuth 180, backtrack on) + Ineichen clear-sky + Hay-Davies + Faiman + PVWatts vs real PVDAQ 9068 June 2024 (imported with `seed.pvdaq`, 15-min, 29 days). PVDAQ metadata gives no gcr, max_angle or axis geometry (tilt 0 / azimuth 180 only) and the files contain no GHI or ambient temperature, so gcr 0.35 and max_angle 60 were assumptions and temp_air was 25 C. Result (not tuned): all days model/measured AC energy 1.22 (June had many cloudy days; a clear-sky model cannot be compared there); on days picked as clear from measured POA smoothness the ratio depended on the selection rule: 1.057 (5 days), 0.951 (2 days), 1.179 (23 days); 15-min RMSE 9 to 23 % of mean AC on those days. The fixed-tilt 0/180 baseline on the same 5 clear days was 0.795 (about -20 %). Sign and size of the error change with the day filter and unmetadata'd parameters; with a 5-10 % alert threshold that is not a trustworthy baseline, so the 'unsupported' behaviour ships. Revisit with measured GHI/ambient and real gcr/max_angle. | Never alert on a baseline known to be invalid; never ship a tracker model whose error is unquantified. |
| E14 | 2026-11-05 | Money text is currency-aware. Summary text already used the symbol/"unquantified" wording. Schema default is now `unset`; description no longer says USD. Not changed (outside `physics/`): the static `GET /diagnosis/taxonomy` text still contains "($/kW)" because the golden taxonomy fixture pins it; `api/support/revenue.py` prices inspection faults in USD (sd-backend). | Product is INR-centric; no invented tariff or currency. |
| E15 | 2026-11-05 | Tracker marker durability (no migration). `is_tracker_plant` matches the marker case-, whitespace- and punctuation-insensitively (regex over "single axis tracker fixed tilt baseline invalid", optional brackets); prose like "single-axis tracker site" is not flagged. Only the importer/seed can set the marker: it writes `Plant` rows straight through the ORM, while the plants API service (`plant_service.create_plant` / `update_plant`; there is no PATCH route) rejects any marker in `location` on create and on update of a non-tracker plant with 422 ("reserved"), and on update of an existing tracker plant it preserves the flag by stripping variants from the new text and re-appending the canonical marker (the location text stays editable). `/diagnosis/alert/{id}` now returns the same 422 `baseline_unsupported_for_trackers` for tracker plants (checked before returning any stored diagnosis).

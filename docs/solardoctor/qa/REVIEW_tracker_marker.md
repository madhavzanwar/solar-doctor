## Findings (severity-ranked)
- LOW, importer re-import does not repair a plant: `write_mapped` only creates the plant when absent; an existing PVDAQ row keeps its old location. A DB already stripped by the pre-fix PUT stays unflagged after re-import (marker "survives" only because nothing rewrites it). Repro: strip marker in DB, run seed.pvdaq again, is_tracker_plant stays False. Suggest sd-backend/seed re-assert the marker (or ship the mount column).
- LOW, importer location is not bounded: `_location` appends the marker to the PVDAQ site string without the 512 cap that `with_marker` enforces; on Postgres a >455-char site location would error (not realistic for PVDAQ metadata).
- LOW, cosmetic/spoof: marker-lookalikes with Cyrillic/fullwidth/in-word zero-width/HTML entities are accepted and displayed on fixed plants, so a plant can look like a tracker in the UI without being one. Conversely PUT on a tracker leaves residue: partial prefix ("[single-axis tracker " + canonical marker) and a double space when the marker was mid-string. No effect on the guard.
- LOW, design (carried over): marker is still free-text; recommended mount/tracking column + migration (DECISIONS E15 follow-up). `GET /diagnosis/plant/{id}` for a tracker still lists previously stored diagnoses, and /diagnose with caller values plus alert_id stores a diagnosis (200) for a tracker plant; consistent with the stated policy.
- LOW, DELETE (soft) then no way to re-create the same marker via API, so tracker plants cannot be hand-created or restored through the API; intended, note for ops.
